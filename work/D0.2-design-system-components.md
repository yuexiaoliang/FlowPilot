# D0.2 — Design System and Contextual Components

## Role

Product/UX Builder

## Phase

D0 — Design Contract

## Goal

Define the implementation-ready visual foundation and reusable contextual UI
primitives that follow the accepted D0.1 interaction hierarchy.

## Why now

D0.1 is accepted by Gatekeeper. The next bounded slice is the design system and
component contract needed before screen specifications and the end-to-end flow.

## In scope

Create:

- `design/DESIGN-SYSTEM.md`
- `design/COMPONENTS.md`
- matching Chinese mirrors under `design/zh-CN/`

The design-system contract must define the visual and interaction foundations:

- color and semantic state tokens
- typography, readable measure, spacing, sizing, radius, elevation, and density
- focus, keyboard, zoom, contrast, reduced motion, and status-announcement rules
- restrained motion and transition rules consistent with progressive disclosure

The component contract must define purpose, placement, trigger, content hierarchy,
interaction, accessibility, and applicable states for reusable contextual
primitives, including:

- intent editor and semantic references
- understanding review and ambiguity resolver
- Source connection/permission picker
- InputBundle preview
- confirmation card
- execution progress and recovery
- Human Takeover
- result and Inspect details affordance
- Inspector sections, evidence, and repair diff

For every applicable component, specify idle, loading, success, failure, paused,
and disabled behavior without exposing internal IDs or workflow DSL on the
ordinary path. Keep Simple / Execution / Inspection placement explicit.

## Out of scope

- `design/SCREEN-SPECS.md` or `design/FLOWS.md`
- React/Electron implementation or P0 prototype work
- new product entities, navigation destinations, or architecture decisions
- real Source, AI, browser, persistence, or runtime functionality

## Constraints

- Preserve “Simple by default. Transparent on demand.”
- Natural language/Markdown remains the authoring control plane.
- Users write semantics; the system stores references.
- Contextual UI appears only for a current observation, choice, comparison,
  approval, or intervention need.
- Professional detail remains inspectable without becoming permanent clutter.
- No user-facing IDs, cron, selectors, workflow nodes, or hidden DSL.
- Written contract is behavioral authority; visual references cannot override it.
- Maintain English canonical docs and synchronized Chinese mirrors.

## Acceptance mapping

Acceptance: D0 criterion 9 and criterion 14, with preservation checks for
criteria 2, 6–8, and 13, plus Global Definition of Done (product alignment and
documentation).

## Validation

- Review each token and component against `DESIGN-PRINCIPLES.md` and
  `INTERACTION-MODEL.md`.
- Verify every listed component has an explicit trigger, layer placement, and
  all applicable states.
- Verify keyboard, focus, zoom, contrast, reduced-motion, and announcement
  behavior is specified.
- Verify default surfaces do not require or expose IDs, DSL, raw logs, or dense
  dashboard structure.
- Verify English and Chinese heading structures and semantics match.
- Run repository text checks for trailing whitespace and non-empty artifacts.

## Stop conditions

Stop and escalate if:

- a component decision changes Goal, Task, Source, InputBundle, Flow, or Run
  semantics;
- a new permanent top-level destination is required;
- a state cannot be placed consistently on Simple, Execution, or Inspection;
- a component would require a user-facing DSL or hidden permission expansion.
